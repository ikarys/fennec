# Security audit, 2026-11-10

## Summary

Every test that `SECURITY.md` cites exists, and all 45 cited `fennec` tests pass
(`cargo test -p fennec`, 135 security-related tests selected, 0 failed). The sandbox e2e
tests ran against a working bwrap on this machine. `cargo audit` reports 0
vulnerabilities and 0 warnings. `gitleaks` scanned 2604 commits and found no leaks.
Reading the code confirmed the guard, the login gate, the path guards, git hook
suppression, the SQL (every query uses parameters), the XSS sinks (model HTML only ever
runs in an opaque origin, Mermaid goes through `<img>`) and the SSRF guard.

One issue sets the verdict to fail. When "Network for commands" is on, a sandboxed
command counts as a local caller of fennec's own API. It can then turn the sandbox off,
enable an installed plugin, or call integrate. The "not protected" lists in
`SECURITY.md` and `docs/sandbox.md` describe this only as "drive fennec, answer an
approval, start a turn". `AGENTS.md` rules 1 and 2 state the opposite as absolutes.

The other findings are about coverage:
- No test covers the refusal to start remote access without a password.
- The `/raw` CSP claim's cited tests check only the extension filter, never the header.
- The evidence workflow holds a write token and runs CI tools that are not pinned.
- Three sandbox e2e tests can pass without the sandbox ever running.
- Some citations are stale or missing.

Commands run: `cargo test -p fennec -- <security filters>` (TMPDIR private), `cargo audit --json`,
`gitleaks git --no-banner --redact .`. Not run: `cargo test -p rules` (the caller limited targeted
runs to `-p fennec`), clippy (run by the caller through `just check`).

### Finding 1: Close or fully document the sandboxed command's access to fennec's own API
- Severity: DOC-WRONG
- Requirement: AGENTS.md rules 1 and 2 ("No agent ... commits to the human's branch", "An agent can never install or enable a plugin"); SECURITY.md threat model (the sandbox is the wall).
- Where: entry is a sandboxed `run_command` with network on (`crates/fennec/src/sandbox.rs:451` `--share-net`). It reaches `127.0.0.1:7777`, where `crates/fennec/src/web/guard.rs:46` treats a loopback peer with a local `Host` and no `Origin` as `Caller::Local`. The sinks are `POST /api/settings` → `crates/fennec/src/web/routes/settings_routes.rs:279` (`sandbox.enabled: false`), `POST /api/plugins` → `crates/fennec/src/web/routes/plugin_routes.rs:79`, and `POST /api/sessions/{id}/integrate` → `crates/fennec/src/web/routes.rs:273`. The understated text is in `SECURITY.md:66` and `docs/sandbox.md:93`.
- Confirmed by: reading the entry point, guard and handlers above. No request was sent (attacking a running service is out of scope).
- Problem: a prompt-injected command can run `curl -H 'Content-Type: application/json' -d … http://127.0.0.1:7777/api/settings` and switch the sandbox off for every later command, which escapes the wall. The same route lets it enable an installed plugin or ask for integration. The documents only say "drive fennec, answer an approval, start a turn", and AGENTS.md states rules 1 and 2 with no exception.
- Fix: preferably close the gap. Require a per-launch secret for local callers, kept in the hidden data dir and handed to the UI page, so a sandboxed command cannot read it, and add a test that a local POST without it gets 403. Otherwise, name the full impact (sandbox off, plugin enable, integrate) in SECURITY.md, docs/sandbox.md and as an exception to AGENTS.md rules 1 and 2.

### Finding 2: Test that remote access refuses to start without a password
- Severity: PAINFUL
- Requirement: SECURITY.md:24 "Remote access is refused to start without a password hash."
- Where: `crates/fennec/src/web.rs:224` (`serve`); `crates/fennec/src/web/routes/server_routes.rs:54` (400 when `remote` without password)
- Confirmed by: grep for the error text and the `is_loopback` checks finds no test; none of the cited tests reach `serve`.
- Problem: if the only check that stops fennec from listening on the network without a password were dropped, no test would fail.
- Fix: move the check into a pure function (listen address, password option → result) with a test, and add a route test for `server_routes.rs:54`. Cite both in SECURITY.md.

### Finding 3: Assert the sandbox CSP header on raw, preview and canvas responses
- Severity: PAINFUL
- Requirement: SECURITY.md:29 ("with a sandbox `Content-Security-Policy` and `nosniff`"); docs/api.md:817 and 828 (model HTML runs in an opaque origin)
- Where: `crates/fennec/src/web/routes/file_routes.rs:63-70`, `crates/fennec/src/web/routes/preview.rs:30-34`, `crates/fennec/src/web/routes/canvas_routes.rs:178-183`
- Confirmed by: reading the cited tests. They call `read_image` and check the extension filter only. The only CSP test, `crates/canvas/src/format.rs::sandbox_csp_is_none_only_for_real_pdf`, covers the function and not that the routes send its result.
- Problem: the header is what stops model-written HTML or SVG from running with fennec's origin and driving the API. A route that forgets it would still pass every test.
- Fix: one route-level test per endpoint (`test_support` app, a socket pair) asserting the `Content-Security-Policy` and `X-Content-Type-Options` headers. Cite them in the SECURITY.md row.

### Finding 4: Pin the tools the write-token workflows run
- Severity: PAINFUL
- Requirement: step 21, no unpinned third-party items where a token can write.
- Where: `.github/workflows/convention.yml:12` (`contents: write`) with `:53` `cargo install --locked --git https://github.com/ikarys/vibecoding-convention vibecheck` (no `--rev`/`--tag`), `:50` `npx -y jscpd@4`, `:38` `taiki-e/install-action@v2`. All actions in every workflow are pinned by tag, not by SHA (`dtolnay/rust-toolchain@stable`, `Swatinem/rust-cache@v2`, `googleapis/release-please-action@v5` at `release-please.yml:19` with `contents`/`pull-requests: write`). `ci.yml` downloads gitleaks with no checksum check.
- Confirmed by: reading the workflow files.
- Problem: a new commit on another repository's default branch, or a moved tag, runs on `main` with a token that can push to it.
- Fix: install `vibecheck` with `--tag` or `--rev`, pin `jscpd` to an exact version, and pin third-party actions by commit SHA (Dependabot can bump them). Check the gitleaks tarball against its published checksum.

### Finding 5: Make the sandbox e2e tests prove the sandbox ran
- Severity: MINOR
- Requirement: a test must assert the claim, not just exercise a code path.
- Where: `crates/fennec/src/sandbox.rs:968` (`e2e_the_root_filesystem_is_read_only`), `:940` (`e2e_container_daemon_sockets_are_hidden`), `:1117` (`e2e_git_metadata_is_read_only_in_the_workdir`), and the silent `return` when bwrap is missing (`:902`)
- Confirmed by: reading. These three only assert `!status.success()`. A bwrap that exits non-zero, for example when AppArmor blocks user namespaces, makes them pass.
- Problem: on a misconfigured runner they show green while proving nothing. CI's sysctl step and the positive asserts in the network and read-only tests currently cover for this.
- Fix: in each test, first run a positive control command that must succeed (as `e2e_read_only_paths_are_read_only_in_the_workdir` already does). Fail instead of returning when `CI` is set and bwrap is missing.

### Finding 6: Cite the tests behind the hidden-secrets, protected-file and Seatbelt claims
- Severity: MINOR
- Requirement: every security claim points to the test that proves it.
- Where: SECURITY.md:26 (hidden dirs: proven by the uncited `sandbox.rs::from_prefs_lists_only_paths_that_exist` at `:829` and `e2e_a_hidden_dir_is_not_readable` at `:994`; Seatbelt: `crates/fennec/src/sandbox/seatbelt.rs:377-` e2e tests, which run only on macOS and are absent from CI); the integration row (protected files: `domain/integration.rs:493` `architecture_violations_block_after_protected_files`, uncited)
- Confirmed by: reading the cited and uncited tests.
- Problem: a reader checking the table cannot find what proves these sub-claims, and nothing re-runs the macOS claim.
- Fix: add the citations. Mark the Seatbelt tests as "macOS only, run by hand before a release", or run them in the existing macOS build job.

### Finding 7: Replace "(no automated test)" on sealed keys with the tests that exist, and test the save path
- Severity: MINOR
- Requirement: SECURITY.md:37
- Where: `SECURITY.md:37`; `crates/fennec/src/config.rs:414` (`a_sealed_key_opens_with_the_master_key`); the connector's `secret.rs` tests (round trip, nonce, tamper, wrong key, mode 0600); untested sink `crates/fennec/src/web/routes/settings_routes.rs:291-297`
- Confirmed by: reading `config.rs` and llm-providers-connector 0.2.0 `src/secret.rs`.
- Problem: the doc says no test exists when several do. Meanwhile the fennec-side guarantee, that a key POSTed in plain text is stored sealed, has none.
- Fix: cite the existing tests and add one route test: save `{"plain": "k"}`, then assert the stored preferences hold `ApiKey::Sealed` and no `"k"`.
